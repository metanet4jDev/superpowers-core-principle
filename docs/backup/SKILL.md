# Core Principle

## Overview

在头脑风暴前，先建立核心认知，再给方案。

**核心原则：** 认知必须简洁、精确、可验证，且必须按固定顺序理解系统，避免在压力下直接跳到方案、实现或结论。

**与 `brainstorming` 的关系：** `brainstorming` 决定如何进入设计讨论；本技能决定进入讨论前必须先建立什么认知骨架，
以及在设计讨论过程中如何完善核心认知

**完整性原则：** 7 个维度不是标题占位。每一维都必须说到“足以支撑后续设计”的最核心信息；如果信息不足，就明确写 `待确认`，不能跳过。

## When to Use

**Use when：**
- 开始系统架构、功能设计、组件设计、行为修改前的头脑风暴
- 开始需求澄清、领域建模、business rules 梳理、state transition 分析时
- 需要先统一系统理解，再进入方案、拆解、设计或实现
- 面对复杂业务规则、状态流转、实体关系、边界条件时
- 用户要求“先想清楚再做”或场景本身容易误改行为时
- 已经开始设计，但发现关系没说清、属性没归属、状态没闭环、界限没落到条件和变化时

**Do not use when：**
- 只是查一个现成 API、命令或语法
- 只是做机械替换，没有系统理解成本
- 只需要遵循 brainstorming 的对话流程，而不需要额外澄清实体、状态、界限

## Core Pattern

必须按下面顺序建立认知，不能跳步，不能重排：

| 顺序 | 维度 | 必须回答的问题 | 
| --- | --- | --- |
| 1 | 结构 | 系统、子系统、模块、组件如何分层和协作？ |
| 2 | 分类 | 有哪些关键实体？它们如何命名和归类？ |
| 3 | 关系 | 实体之间依附、关联、约束关系是什么？ |
| 4 | 属性 | 关键实体有哪些属性？属性的核心要点 |
| 5 | 状态 | 初始、中间、最终状态是什么？状态如何迁移和约束？核心要点 |
| 6 | 功能 | 系统提供什么能力？每个功能的目的是什么？ |
| 7 | 界限 | 遵循give->when->then模式，功能会改变哪些实体的关系、属性和状态？什么条件决定功能可用或不可用？ 输入是什么，在什么情况下，产生对应的输出是什么？|

说明
- 属性核心要点包括 ：类型是什么、哪些属性决定实体的唯一性、属性是否可编辑、是否必填、长度、精度是什么？

如果某一步说不清，就不要进入下一步。

> 输出约定：
- 对每一个功能模块，你都被要求按照核心认知的模式进行设计和文档输出
- 关系、属性和状态的文档部分，作为文档的前置环节、要按照实体维度分节描述，不要所有实体揉和到一起。属性建议使用表格，表达更清晰
- 需要详细进行功能描述、功能描述需要结合界限形成完整论述，遵循give->when->then 模式 
        give 输入包括哪些实体,状态、属性的值分别是什么 
        when 什么条件（属性、状态）决定功能可用或不可用
        then 会改变哪些实体的关系、属性和状态？输出是什么？
        exception 有哪些异常场景？ 
- 功能设计需要按照功能模块划分章节。每个模块下的每个功能点对应一个可执行任务，逐个功能点进行描述、使你的伙伴能够明确知道，有哪些实体，以及哪些实体的关系、属性、状态参与到这个功能点中


> 操作规则：
- 前维度如果暂时说不清，就先在该维度下写 `待确认` 补足缺口，再进入下一维；不能把整一维留空后继续往下走

> 图表
- 图表默认输出采用plantuml格式，有必要可参考官网 https://plantuml.com/zh/
- 描述结构，根据复杂度，判断是否需要给出 流程图或者时序图等，一般超过三个独立子系统，模块之间的交互建议给图

### 每一维的最低完成标准

| 维度 | 最低完成标准 | 常见缺漏 |
| --- | --- | --- |
| 结构 | 说清分层、模块职责、协作链路；各“层次怎么协作”？ | 只列模块名，不说谁驱动谁 |
| 分类 | 列出关键实体；分类回答“有哪些实体” | 只写抽象名词，如“数据、流程、配置” |
| 关系 | 至少说清依附关系、影响方向；能说基数时直接说 `1-N`、`N-1` | 只说“有关联”，不说谁影响谁 |
| 属性 | 属性必须挂到具体实体；列出会影响判断的关键属性，并且要将属性的核心要点罗列清楚 | 只堆字段名，不说明属于谁、是否关键 |
| 状态 | 说清核心要点，必要时给出状态图 | 只有状态名，没有迁移或约束 |
| 功能 | 清楚表达功能的作用对象与目的 | 只写“支持新增/编辑/删除” |
| 界限 | 承接功能结果，同时说“功能引起什么变化”和“什么条件阻止功能” | 只讲风险，不讲可用条件和副作用 |

### 缺信息时的处理

- 不能因为信息不足就跳过某一维
- 直接写 `待确认`，并指出缺的是哪一个实体、关系、属性、状态、条件
- 待确认的问题必须是后续设计会真的依赖的，不要泛泛提问
- 可以带着 `待确认` 进入下一维，但前提是当前维度已经写出最低可验证骨架

### 持续构建
- 在设计过程中，需要根据你的伙伴反馈信息，持续完善构建核心认知，并在设计文档中持续更新


## Implementation

### 输出要求

- 文字简洁、准确、精要、目的明确、可验证
- 优先从现有代码、文档、目录、命名、状态流转中提取认知，不额外制造文档、只需要建立文件索引，便于查找即可
- 如果代码已经能表达，就不要重复维护额外说明
- 对于属性和状态的注释，可以在代码文件中直接补充的，优先补充到代码文件中
- 如果后续继续展开设计，始终回到这 7 维补齐；不要在后续轮次里把关系、属性、状态、界限再次讲丢
- 必须在设计文档中将七维认知所要求的部分描写清楚，目的是通过设计文档，对系统有准确清晰的把握
- 功能负责交代动作、目的、作用对象；界限负责交代这些动作带来的变化、输出和被限制的条件


## Common Mistakes

| 错误 | 修正 |
| --- | --- |
| 直接给方案，不先建立认知 | 先按 7 个维度输出完整认知骨架 |
| 只讲功能，不讲实体、状态、界限 | 补齐分类、属性、状态、界限后再继续 |
| 关系只写“有关联” | 明确谁依附谁、谁影响谁，能写基数就写 |
| 属性只列字段名，不挂到实体,并且对核心要点认知完整清楚 | 用“实体.属性”表达关键字段 |
| 状态只有名称，没有迁移 | 补上关键迁移动作和触发条件 |
| 把“界限”写成泛泛风险 | 明确“什么变化会发生”与“什么条件禁止功能” |
| 为了说明问题新建很多文档 | 先读代码，能从代码表达就不额外维护 |
| 因为时间紧就省略认知步骤 | 时间越紧，越要先固定认知顺序 |
| 第一轮讲清了，后续展开又把关系/属性/状态讲丢 | 后续所有展开都要回到 7 维继续补齐 |

## Red Flags

- “先直接给方案，后面再补理解”
- “用户要求简洁，所以分类、状态、界限先不写”
- “大概知道系统怎么跑就够了”
- “先写功能清单，实体和状态之后再补”
- “多写一份文档更保险”
- “关系先模糊写一下，后面再补”
- “属性不用挂到实体，先列字段名就行”
- “状态名字有了，迁移以后再说”

这些都表示：你正在跳过核心认知，应立即回到 7 步顺序。

## Completion Check

完成一次核心认知后，需要自查
- 是否按照 [每一维的最低完成标准]章节所要求的完成、任一项答不上来，就说明认知还不完整。
- 核心认知是否有计划落入到设计文档中，能够帮助你的伙伴形成对系统的核心认知的准确完整的理解

## Purpose
核心认知的目的，是为后续工作建立一个稳定一致、可扩展、可验证的环境：

- 稳定一致：整个工作过程中的理解保持一致，不随上下文漂移
- 可扩展：新增规则、模块、行为时，有明确挂载点
- 可验证：可以独立检查认知是否完整，并据此修正错误理解
