# 跟踪计划执行

## 目标

把 `task_plan.md` 作为计划执行的持久 checkpoint。每完成一个动作立即更新文件；恢复时以文件和实际产物确定下一步。

## 状态契约

- 阶段状态只按 `pending → in_progress → complete` 迁移。
- 执行中，`当前阶段` 必须指向唯一的 `in_progress` 阶段；全部完成时，各阶段均为 `complete`，`当前阶段` 为 `已完成`。
- 已完成阶段的复选框全部为 `[x]`；当前阶段从第一个 `[ ]` 继续。
- 后续阶段保持 `pending`。
- 动作通过其验证条件后，才能把复选框改为 `[x]`。
- 决策写入“已做决策”，失败写入“遇到的错误”；计划文件保存事实，聊天记录不承担恢复依据。

## 执行步骤

### 1. 加载 checkpoint

优先使用用户指定的 `task_plan.md`；否则使用当前任务目录中的同名文件。存在多个候选文件时，先确认目标文件。完整读取计划和当前任务涉及的产物。

目标文件尚不存在、但待执行计划已明确时，读取 `/home/haodev/.skills/planning-with-files/skills/planning-with-files-zh/templates/task_plan.md`，在计划目录创建 `task_plan.md`，并用真实目标、阶段和动作替换占位内容。

**完成条件：** 已确定唯一计划文件，并读到目标、当前阶段、所有阶段状态、复选框、决策和错误。

### 2. 初始化或恢复

计划尚未执行时，将第一个未完成阶段设为 `in_progress`，同步 `当前阶段`。

恢复中断计划时：

1. 全部复选框均为 `[x]` 时，按“状态契约”收敛为已完成并停止执行。
2. 否则找到最早包含 `[ ]` 的阶段。
3. 检查该阶段第一个未完成动作对应的文件、命令结果或外部状态。
4. 动作已有合格结果时，补做验证并标记 `[x]`；结果缺失或不合格时，从该动作继续。
5. 按“状态契约”纠正阶段状态，并在“备注”记录恢复点和纠正原因。

**完成条件：** 执行中只有一个 `in_progress` 阶段，`当前阶段` 与其一致，下一动作明确且不会盲目重复副作用；或计划已收敛为完成状态。

### 3. 执行一个动作

执行当前阶段第一个 `[ ]` 动作。重大决策前重新读取 `task_plan.md`。动作可能产生重复副作用时，先检查实际状态，再决定执行或仅验证已有结果。

动作完成后立即：

1. 执行该动作要求的最小验证。
2. 将对应复选框改为 `[x]`。
3. 保存所有更新。

**完成条件：** 动作结果已验证，复选框和相关记录已持久化。

### 4. 记录偏差

产生新决策时，立即填写“已做决策”的决策与理由。动作失败时，保持复选框为 `[ ]`，在“遇到的错误”记录错误、累计尝试次数和下一种方案，然后保存计划。

计划目标、范围或阶段需要变化时，暂停执行并取得用户确认；保留已执行记录，以新增阶段承接变化。

**完成条件：** 计划能解释当前结果、失败次数和下一步；恢复者无需依赖聊天上下文。

### 5. 推进阶段

当前阶段仍有 `[ ]` 时，回到步骤 3。当前阶段全部为 `[x]` 时，将其设为 `complete`；存在下一阶段时，将下一阶段设为 `in_progress` 并同步 `当前阶段`。

最终阶段完成时，将其设为 `complete`，把 `当前阶段` 改为 `已完成`。

**完成条件：** 阶段状态满足“状态契约”，并已保存到磁盘。

### 6. 暂停或交付

主动暂停前，重新读取计划，确认已完成动作均为 `[x]`、当前未完成动作仍为 `[ ]`、决策和错误已记录。恢复执行时重新从步骤 1 开始。

全部交付前，确认所有阶段为 `complete`、所有复选框为 `[x]`、目标和输出文件均已验证。

**完成条件：** 中断后可从唯一未完成动作恢复；全部完成时计划不存在未完成项。
