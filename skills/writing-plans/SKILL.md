# 编写实现计划

## 目标与边界

从已批准的详细设计事实源生成实现计划。计划必须让熟练但不了解代码库和业务的工程师能完成实现、测试和提交。

**仅在用户明确要求编写计划时使用；不得因“现在应该先写计划”自动触发。** 开始时声明：

> "我正在使用 writing-plans 技能编写实现计划。"

硬规则：

- 只消费设计事实；不得新增、删除或语义改写设计。
- 事实源缺失或与计划不一致时，先用 `writing-detailed-design` 修设计，再写计划。
- 计划审查不得自动执行，只能由用户明确触发。
- 涉及代码修改的任务，提交前必须完成规范要求的代码和测试审查，并修复发现的问题；否则不得提交或标记完成。
- 任务默认拆成 2-5 分钟步骤；坚持 DRY、YAGNI、TDD 和频繁提交。
- 每个任务必须给出准确文件路径、单元测试清单、预期验证语义和执行步骤。
- 不得写实际测试代码、实现代码、具体测试命令、验证命令或提交命令。

## 路径契约

写入或引用任务级路径前，必须用 `superpowers:document-workspace-layout` 解析：

- `DESIGN_DOC_PATH`
- `CORE_COGNITION_PATH`
- `SPECS_DIR`
- `DESIGN_ARTIFACTS_DIR`
- `PLAN_PATH`
- `PLAN_CHANGELOG`
- `PLAN_WORKSPACE_DIR`
- `TASK_WORKSPACE_DIR`

路径规则：

- `PLAN_PATH` 是唯一正式入口，文件名固定为 `implementation-plan.md`。
- 拆分时，入口仍为 `PLAN_PATH`；分片只能位于同一 `PLAN_WORKSPACE_DIR`，命名为 `implementation-plan-part-01.md`、`implementation-plan-part-02.md`。
- `planning-with-files-zh` 的 `task_plan.md`、`findings.md`、`progress.md` 必须与 `PLAN_PATH` 同目录。

## 事实源与范围闸门

写计划前确认：

- 设计文档存在且已批准。
- 独立 `CORE_COGNITION_PATH` 存在，并被设计文档引用。
- 主文档已引用配套文件，且必要内容存在。
- 计划未相对设计文档新增、删减或语义改写。

每个任务或步骤必须标注事实来源章节，如 `详细设计 §6.2`、`核心认知 §3`。以下情况必须阻塞：

- 源文档缺少必要事实：先更新设计。
- 实现反馈改变行为、状态、接口或存储：先更新设计/核心认知，再更新计划。
- 无法证明任务与源文档同步。

规格覆盖多个独立子系统且尚未拆成多个设计或计划时，停止并建议拆分。每份计划必须能独立产出可工作、可测试的软件。检查：

- 是否跨多个独立子系统。
- 是否需要多个发布或迁移阶段。
- 是否存在无法在单份计划中串行完成的工作流。
- 是否已有计划漂移，需先同步旧计划。

## 文件结构

定义任务前，先列出：

- 新建、修改的文件及各自职责。
- 测试文件及覆盖行为。
- 作为事实来源的配套设计文件。

文件按职责拆分，不按技术层机械拆分；经常一起修改的文件可合并。遵循现有代码库模式，不做无关重构。

## 任务顺序闸门

计划中必须原样包含：

```markdown
### 0. 任务顺序闸门（强制）

- [ ] 当前任务所有步骤完成后，将当前任务所有复选框标记为 `[x]`。
- [ ] 当前任务未标记完成前，不得开始下一个任务。
- [ ] 涉及代码修改的任务必须先完成 TDD、规范审查、问题修复和提交，才能标记完成。
```

每个任务最后一步必须写明“标记当前任务已完成”。涉及代码修改的任务，必须先审查代码和测试、修复问题，再提交。

## 计划头部

`PLAN_PATH` 入口文件必须以如下头部开头：

```markdown
# [功能名称] 实现计划

> **事实源声明（强制）**
> 本计划严格依据详细设计和核心认知事实源文档编写，不新增、不删除、不语义改写。
>
> 详细设计文档（绝对路径）：`/ABS/PATH/TO/design-codex.md`
> 核心认知文档（绝对路径）：`/ABS/PATH/TO/core-cognition.md`
>
> **给执行代理的要求：** 必须使用 `superpowers:subagent-driven-development`（如果支持子代理）或 `superpowers:executing-plans` 执行本计划。步骤必须使用复选框（`- [ ]`）语法跟踪。

**目标：** [一句话说明本计划要实现什么]

**架构：** [2-3 句话说明实现方式]

**技术栈：** [关键技术/库]

**代码仓库与分支：**

- 代码仓库：[仓库本体的绝对路径]（若用 git worktree，须同时给出开发目录）
- 开发目录：[日常代码读写的绝对路径]
- 开发分支：[分支名]

---

```

头部必须满足：

- 详细设计和独立核心认知文档均使用绝对路径。
- 明确代码仓库、开发目录和开发分支；使用 git worktree 时，区分仓库本体与开发目录。
- 拆分计划时，入口文件列出所有分片及执行顺序。

## 任务模板

每个任务必须形成一组独立成形的改动。所有涉及代码修改的任务都使用以下模板；实现步骤必须要求按 `skills/test-driven-development/SKILL.md` 完成完整 TDD，并保证必要注释与详细设计/核心认知一致。

````markdown
### 任务 N：[组件名称]

**事实来源：** 详细设计 §x.y；核心认知 §a.b

**涉及文件：**
- 新建：`exact/path/to/file.py`
- 修改：`exact/path/to/existing.py:123-145`
- 测试：`tests/exact/path/to/test.py`

- [ ] **步骤 1：列出单元测试**

只列测试文件、测试方法和覆盖场景，不写测试代码。

**单元测试清单：**
- `tests/exact/path/to/test.py::test_specific_behavior`：覆盖 [具体行为/边界/异常语义]

**预期验证语义：**
- 失败验证：新增单元测试先以符合预期的原因失败。
- 通过验证：最小实现和必要重构后，相关单元测试通过，行为和必要注释与事实来源一致。

- [ ] **步骤 2：按 TDD 技能完成测试与实现**

按 `skills/test-driven-development/SKILL.md` 执行完整流程：先写失败测试，确认失败原因正确，完成最小实现，确认测试通过，必要时重构并保持测试通过。实现中的必要注释必须与详细设计 §x.y 和核心认知 §a.b 一致。

- [ ] **步骤 3：按规范审查代码和测试，并修复问题**

按 `/home/haodev/worksapces/harness-hh/standards/code-rules.md` 和 `/home/haodev/worksapces/harness-hh/standards/testing.md` 审查本任务改动。修复审查发现的问题后，再进入提交步骤。

- [ ] **步骤 4：提交**

审查问题修复完成后提交本任务改动，不写具体提交命令。

- [ ] **最终步骤：标记任务 N 已完成，再进入任务 N+1**

将当前任务所有复选框标记为 `[x]`。当前任务完成前，不得开始任务 N+1。
````

代码审查是提交前强制步骤，不再作为可选的独立审查闸门。

## 计划拆分

单个文件能容纳全部内容时，将完整计划写入 `PLAN_PATH`。超出限制时：

- `PLAN_PATH` 仍是唯一入口，保存事实来源声明、目标、架构、技术栈和分片顺序。
- 可执行内容写入 `implementation-plan-part-01.md`、`implementation-plan-part-02.md`。
- 每个分片以简短标题开头，并回指 `implementation-plan.md`。
- 每个分块必须完整放在单个文件中，不得跨文件。
- 每个计划文件 `<=1000` 行；每个 `## Chunk N: <name>` 分块 `<=500` 行。

## 禁止项

计划不得出现：

- `TBD`、`TODO`、`implement later`、`fill in details`。
- “添加适当的异常处理”但无具体错误语义。
- “添加校验”但无具体字段、条件、预期错误。
- “补充上述测试”但无测试文件、测试方法和覆盖场景。
- “类似任务 N”。
- 只写“做什么”，不写“怎么做”。
- 引用类型、函数或方法，但任何任务都未定义它们。

## 用户触发的计划审查

不得自动审查。每完成一个计划文件或分块后，只能提示：

> "计划已保存。如果需要我审查计划，请直接告诉我。"

仅当用户明确要求“review / 审查 / 检查计划”时，才用 `plan-document-reviewer-prompt.md` 派发计划审查代理：

1. 仅提供当前分块、`DESIGN_DOC_PATH`、`CORE_COGNITION_PATH` 和配套文件列表；不传会话历史。
2. 返回 `Issues Found` 时，按用户要求修改；是否复审仍须用户明确指令。
3. 超过 3 轮仍未通过时，交由人工指导。

出现任一情况必须判定审查失败：计划/设计漂移、事实来源缺失、分块大小违规、任务步骤不可执行、TDD 流程缺失，或实现步骤未要求必要注释与详细设计/核心认知一致。

## 交接与完成检查

保存后输出：

> "计划已完成并保存到 `<PLAN_PATH>`（若已拆分，按入口文件中的 part 顺序执行）。"

执行路径：支持子代理时用 `superpowers:subagent-driven-development`；否则用 `superpowers:executing-plans` 分批执行并保留人工检查点。`writing-plans` 阶段不得直接实现。

完成前确认：

- `PLAN_PATH` 存在且是唯一入口；事实来源均为绝对路径。
- 每个任务包含来源章节、文件范围、单元测试清单、预期验证语义和提交步骤。
- 每个任务引用 `skills/test-driven-development/SKILL.md`，并要求完整 TDD。
- 每个代码修改任务要求按代码和测试规范审查，修复后再提交。
- 每个实现步骤要求必要注释与详细设计/核心认知一致。
- 计划无实际测试代码、实现代码、具体测试命令、验证命令或提交命令。
- 计划无占位符、无语义漂移，且不了解背景的工程师可执行。
