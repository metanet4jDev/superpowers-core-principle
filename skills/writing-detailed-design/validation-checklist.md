# Detailed Design Validation Checklist

仅在用户明确要求验证详细设计时使用。不要自动触发。

本清单只检查详细设计主文档和配套文件；核心认知只检查“被引用、未重复、被正确消费”，不检查其内容是否完整。

## 验证步骤

### 1. 主文档职责

检查主文档是否覆盖：

- 背景和目标。
- 范围和非目标。
- 执行、上线、兼容约束。
- 核心认知引用：路径、版本或章节索引。
- 方案比选或设计决策。
- 总体设计、代码锚点、实现约束。
- 功能点详细设计。
- 配套文件引用。
- 接口与验收。
- 风险、待确认、受影响模块/资产。

主文档不应复制完整核心认知、完整 DDL、全量接口字段、完整状态表、完整消息体或实现计划。

### 2. 核心认知消费方式

- 详细设计必须引用独立 `CORE_COGNITION_PATH`。
- 功能点里的实体、关系、属性、状态必须能回到核心认知定位。
- 详细设计可以说明“如何使用核心事实”，不得重新定义核心事实。
- 若详细设计新增事实会改变核心认知，必须先更新核心认知，再更新详细设计。

### 3. 配套文件是否必要且可追踪

按需要检查：

- 类图/接口图：核心接口、类、方法、依赖。
- 时序图/状态图：主链路、分支、状态迁移、补偿。
- 存储变更：表、字段、索引、约束或非关系型结构。
- 运行时状态：cache、消息、任务、TTL、幂等、清理。
- API/事件契约：Controller OpenAPI/Apifox 或事件契约。
- 迁移兼容：灰度、回滚、兼容窗口、数据迁移。
- 联调前置条件：环境、配置、外部依赖、调试顺序。

主文档必须相对引用必要配套文件；配套文件不得与主文档大段重复。

### 4. API/事件契约

若存在 controller 接口契约，按 OpenAPI/Apifox 口径校验：

- 可导入 Apifox 时优先 OpenAPI 3.0.3 YAML；确需兼容旧工具时才用 Swagger 2.0 JSON。
- 只描述 controller 契约：路径、方法、参数位置、请求体、响应体、字段类型、字段可见性、nullable、返回分支、所属模块、兼容例外。
- 不把 service、DAO、SQL、消息队列、数据库表或内部调用链写成接口事实。
- 每个接口有系统/模块/controller 标识，可用 `tags`、`description`、`x-project`、`x-module`、`x-controller`。
- 字段类型具体；URL、状态、布尔标记、数组、固定 DTO 不写成裸 `object`。
- nullable 字段写清何时为 `null`、`null` 表示什么。
- 命中、未命中、空列表、空对象、错误态有明确返回口径。
- 查询接口默认无副作用；若会创建、刷新、发码、补齐或写库，必须显式说明。
- 同一业务对象在多个接口中复用同一 schema。
- 本地 YAML/JSON 解析通过；`paths` 数量与接口清单一致。

非 controller 事件契约写入独立 `<topic>-contract.md`，只描述事件字段、方向、幂等、重试、错误语义和兼容口径。

### 5. 功能点是否能落到实现和测试

每个功能点检查：

- `功能`：动作、目的、作用对象、主路径、失败路径、终止条件、序列图引用。
- `参与实体`：实体、关系、属性、状态，且能回到核心认知定位。
- `界限`：`given / when / then / exception / verify`。
- `when / then / verify` 场景编号一一对应。
- `then` 明确输出、关系变化、属性变化、状态变化；不变化也要说明。
- `verify` 写清怎么验证、验证什么、为什么有效。

### 6. Plan drift

详细设计变更后：

- `PLAN_PATH` 不存在：记录“不涉及既有计划同步”。
- `PLAN_PATH` 存在：检查是否影响计划任务、文件范围、测试或执行顺序。
- 若影响计划但未同步，报告为问题；只有用户要求修正时，才调用 `writing-plans` 更新计划并追加 `PLAN_CHANGELOG`。

```markdown
   - 修正方向：
   - 验证方式：

### Coverage

- 主文档职责：
- 核心认知引用：
- 配套文件：
- API/事件契约：
- 功能点：
- Plan drift：

### Summary

- <是否通过 / 是否需修改>
```
