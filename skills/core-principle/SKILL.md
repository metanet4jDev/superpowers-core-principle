# Core Principle

## Overview

在进入方案、设计或实现前，先建立系统的核心认知骨架。

**核心原则：** 认知必须简洁、精确、可验证，并按固定顺序建立，避免在压力下直接跳到方案、实现或结论。

**与 `brainstorming` 的关系：** 本技能通常作为 `brainstorming` 的前置认知 gate。先补齐核心认知，再进入澄清、方案和设计讨论。

## When to Use

**Use when：**
- 实体、关系、属性、状态或可用条件没有说清，继续设计容易误判时
- 用户要改行为、改规则、改状态流转，但副作用和边界条件还没收束时
- 讨论已经进入方案或实现，但系统理解仍停留在抽象词，缺少可验证骨架时
- 看起来只是小改动，但业务规则、状态迁移或可用条件其实容易误读时
- 用户明确要求“先想清楚再做”，或你已经察觉自己想跳过认知直接给方案时
- 需要先统一系统理解，再决定是否进入方案、拆解、设计或实现时

**Do not use when：**
- 只是查询现成 API、命令或语法
- 只是做机械替换，没有系统理解成本
- 问题局限在局部语法或工具用法，不涉及系统行为和规则判断

## Core Pattern

必须按下面顺序建立认知，不能跳步，不能重排。

| 顺序 | 维度 | 必须回答的问题 |
| --- | --- | --- |
| 1 | 结构 | 系统、子系统、模块、组件如何分层和协作？如果是多子系统新系统，每个子系统在总系统中的位置是什么？ |
| 2 | 分类 | 有哪些关键实体？它们如何命名和归类？ |
| 3 | 关系 | 实体之间的依附、关联、约束关系是什么？如果是多子系统新系统，子系统之间的依赖、被依赖、调用和协作关系是什么？ |
| 4 | 属性 | 关键实体有哪些关键属性？类型、唯一性、可编辑性、必填、长度、精度等核心要点是什么？哪些属性决定判断与约束？ |
| 5 | 状态 | 初始、中间、最终状态是什么？状态如何迁移和受约束？ |
| 6 | 功能 | 系统提供什么能力？每个功能的目的和作用对象是什么？ |
| 7 | 界限 | 功能在什么条件下可用或不可用？执行后会改变哪些关系、属性、状态？输出和异常是什么？ |

如果某一步说不清，不要跳过；先把当前维度补到最低可验证骨架。

属性核心要点至少包括：类型、唯一性、可编辑性、必填、长度、精度。只要这些会影响规则判断、接口契约、校验逻辑、状态迁移、输出或存储设计，就必须明确。

## Quick Reference

在进入设计建议前，先给出这 7 行骨架：

```text
结构：
分类：
关系：
属性：
状态：
功能：
界限：
```

`界限` 必须同时覆盖：
- 可用条件和不可用条件
- 执行带来的关系、属性、状态变化
- 输出和异常场景

## Minimum Bar

| 维度 | 最低完成标准 | 常见缺漏 |
| --- | --- | --- |
| 结构 | 说清分层、模块职责、协作链路；多子系统场景下还要说清每个子系统在总系统中的位置 | 只列模块名，不说谁驱动谁、不说子系统为什么存在 |
| 分类 | 列出关键实体，回答“有哪些实体” | 只写抽象词，如“数据、流程、配置” |
| 关系 | 说清依附关系、影响方向；能写基数就写 `1-N`、`N-1`；多子系统场景下说清依赖谁、被谁依赖 | 只说“有关联”，不说谁影响谁、不说跨子系统依赖 |
| 属性 | 属性必须挂到具体实体；列出会影响判断的关键属性，并说明类型、唯一性、可编辑性、必填、长度、精度等核心要点 | 只堆字段名，不说明属于谁、为什么关键、约束是什么 |
| 状态 | 说清状态、迁移、触发条件、约束 | 只有状态名，没有迁移或约束 |
| 功能 | 说清功能点的作用对象、动作、目的；每个功能点应能对应一个明确的可执行任务 | 只写“支持新增/编辑/删除” |
| 界限 | 使用 `given / when / then / exception` 说清输入前提、可用条件、结果变化、输出和异常 | 只讲风险，不讲条件、变化、输出和异常 |

## Handling Unknowns

如果当前维度信息不足，必须先写 `待确认`，明确缺的是哪个实体、关系、属性、状态或条件，再进入下一维。

规则：
- 不能整一维留空
- 不能跳过当前维度，假设后面再补
- `待确认` 必须和后续设计决策直接相关
- 可以带着 `待确认` 进入下一维，但前提是当前维度已经有最低可验证骨架
- 如果内容来自推测而不是代码、文档或明确需求，要直接标成 `待确认`，不要把推测写成定稿
- 如果真实命名尚未确认，不要伪装成现成字段名；先写业务含义，再标 `字段名待确认`
- 如果当前轮次只有用户输入、没有实现锚点，就只写业务含义与规则，不补实现细节猜测
- 如果关键属性的类型、唯一性、可编辑性、必填、长度、精度还不清楚，且它们会影响判断、校验、状态迁移或输出，就必须优先提问或标成 `待确认`

## Implementation

- 默认只覆盖本次任务真正受影响的模块、实体、状态和功能，不必无边界铺满全系统
- 如果是新建多子系统系统，“受影响范围”默认是拆分后识别出的全部目标子系统，不能只先覆盖第一个子系统
- 如果只是单规则、单行为或单链路改动，只围绕该改动展开，不按模块清单机械铺开
- 优先从代码、命名、目录、现有文档、状态流转中提取认知；能落到文件索引时就落到文件索引
- 如果任务明确依赖现有仓库，先给出代码锚点或待核对文件，不要把逻辑概念直接写成真实实现
- 代码已经清楚表达的内容，不重复制造平行文档
- 高压或要求简洁时，每一维用 1-2 句，只保留当前改动真正需要的信息
- 只有在复杂设计、跨模块协作或规则易误解时，才沉淀专门设计文档
- 关系、属性和状态建议按实体分节表达；只有在用户未限制输出形式且表格确实更清晰时，属性才优先用表格
- 后续继续展开设计时，始终回到这 7 维补齐，不丢关系、属性、状态与界限
- 用户明确要求“不额外写文档”或“不要画图”时，直接遵从，不要因为技能默认建议而补文档或补图
- 当属性核心要点会影响规则判断、接口契约、校验逻辑、状态迁移、输出或存储设计时，应在头脑风暴阶段通过提问补齐；补不齐就标 `待确认`

### Design Doc Structure (When Needed)

如果当前任务本来就需要沉淀设计文档，按下面结构组织：

- 先按功能模块划分章节，只覆盖本次任务真正受影响的模块
- 每个模块下，先写“实体与属性”，再写“关系与状态”，最后逐个展开“功能点”
- 每个功能点都应对应一个明确的可执行任务
- `功能` 只负责说明“做什么、为谁做、目的是什么”
- `界限` 只负责说明“什么条件下能做 / 不能做，做了会变什么，输出什么，异常是什么”
- `given / when / then / exception` 只放在 `界限` 中，不要和 `功能` 重复

### Multi-Subsystem Decomposition (When Needed)

如果是从零建立的新系统，并且有充分必要拆分为多个子系统，先协助用户完成子系统拆分，再分别建立每个子系统的核心认知。

规则：
- 先给出总系统视角：总目标、主链路、为什么需要拆成多个子系统
- 再给出子系统清单：每个子系统的职责边界、为什么独立存在
- 然后逐个子系统建立核心认知，而不是只挑一个子系统先讲到底
- 每个子系统的核心认知都必须说明：
  - 它在总系统中的位置
  - 总系统里还存在哪些其他子系统
  - 它依赖哪些子系统
  - 哪些子系统依赖它
  - 它与其他子系统通过什么关系或链路协作
- 如果当前只在做总系统拆分，可以先把字段级属性约束收敛到真正影响子系统边界的部分；不要过早把所有子系统都拉到细字段设计

推荐文档顺序：
- 总系统概览
- 子系统划分与拆分理由
- 子系统依赖关系总览
- 子系统：A
- 子系统：B
- 子系统：C

## Example

下面用“订单退款”说明 `功能` 与 `界限` 的区别。

```markdown
结构：订单模块管理订单状态，支付模块管理退款状态，通知模块负责结果通知。

分类：Order、Payment、RefundRequest。

关系：RefundRequest 依附于 Payment；Payment 状态影响 Order 是否允许继续履约。

属性：
- Order.fulfillmentStatus：enum，非唯一，不可直接编辑，必填，用于表示履约状态
- Payment.amountPaid：decimal，非唯一，不可直接编辑，必填，精度 `18,2`
- Payment.refundStatus：enum，非唯一，不可直接编辑，必填，用于表示退款进度
- RefundRequest.amount：decimal，非唯一，不可编辑，必填，精度 `18,2`

状态：
- Payment：paid -> refunding -> refunded
- Order：confirmed -> fulfilling -> blocked

功能：
- 动作：发起退款；目的：提交退款申请；作用对象：Payment、RefundRequest
- 动作：接收退款回调；目的：同步渠道退款结果；作用对象：Payment
- 动作：阻止后续履约；目的：避免退款后继续履约；作用对象：Order

界限：
- given：订单已支付，且尚未完成履约
- when：退款金额不超过实付金额，支付渠道允许退款
- then：Payment 进入 `refunding` 或 `refunded`，Order 进入 `blocked`，通知模块发送退款结果
- exception：渠道拒绝、重复退款、金额超限
```

这里：
- `功能` 负责说明“系统要做什么、为了什么、作用于谁”
- `界限` 负责说明“什么条件下能做、做了会变什么、输出什么、哪里会失败”

如果要把它落成设计文档，可以继续写成：

```markdown
## 模块：退款履约判断

### 实体与属性

#### 实体：Order

| 属性 | 类型 | 唯一性 | 可编辑 | 必填 | 长度/精度 | 说明 | 待确认 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| fulfillmentStatus | enum | 否 | 否 | 是 | - | 履约状态 | |

#### 实体：RefundRequest

| 属性 | 类型 | 唯一性 | 可编辑 | 必填 | 长度/精度 | 说明 | 待确认 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| amount | decimal | 否 | 否 | 是 | 18,2 | 退款金额 | |

### 关系与状态

- RefundRequest 依附于 Payment
- Payment 状态影响 Order 是否允许继续履约

### 功能点：退款后重算履约资格

- 功能：
  - 动作：重算订单履约资格
  - 目的：保证退款结果与履约状态一致
  - 作用对象：Order
  - 对应任务：实现退款回调后的履约拦截判断

- 参与实体：
  - 实体：Order、Payment、RefundRequest
  - 关系：RefundRequest -> Payment -> Order
  - 属性：Payment.amountPaid、Payment.refundStatus、RefundRequest.amount、Order.fulfillmentStatus
  - 状态：paid、refunding、refunded、blocked

- 界限：
  - given：订单已支付，且尚未完成履约
  - when：退款金额不超过实付金额，支付渠道允许退款
  - then：Payment 进入 `refunding` 或 `refunded`，Order 进入 `blocked`，通知模块发送退款结果
  - exception：渠道拒绝、重复退款、金额超限
```

## Common Mistakes

| 错误 | 修正 |
| --- | --- |
| 直接给方案，不先建立认知 | 先按 7 个维度输出核心认知骨架 |
| 只讲功能，不讲实体、关系、状态和界限 | 补齐分类、关系、属性、状态、界限后再继续 |
| 关系只写“有关联” | 明确谁依附谁、谁影响谁，能写基数就写 |
| 属性只列字段名，不挂到实体 | 用“实体.属性”表达关键字段 |
| 属性只列字段名，不说明类型、唯一性、可编辑性、必填、长度、精度 | 把属性核心要点写清；会影响设计但还不清楚的直接提问或标 `待确认` |
| 状态只有名称，没有迁移 | 补上迁移动作、触发条件和约束 |
| 把 `given / when / then / exception` 同时写在 `功能` 和 `界限` | `功能` 只写动作、目的、对象；`given / when / then / exception` 只放在 `界限` |
| 把“界限”写成泛泛风险 | 明确可用条件、结果变化、输出和异常 |
| 新系统明明需要拆子系统，却直接把所有内容混成一个系统讲 | 先做子系统拆分，再为每个子系统补齐它在总系统中的位置和依赖关系 |
| 脱离代码或文档直接发明字段与状态 | 明确锚点；没有锚点就标 `待确认` |
| 逻辑概念还未落到实现，却写成真实字段名 | 先写业务含义，再标 `字段名待确认` |
| 为了说明问题新建很多文档 | 先读代码；代码能表达就不额外维护 |
| 因为时间紧就省略认知步骤 | 时间越紧，越要先固定认知顺序 |

## Red Flags

- “先直接给方案，后面再补理解”
- “用户要求简洁，所以状态和界限先不写”
- “大概知道系统怎么跑就够了”
- “先写功能清单，实体和状态之后再补”
- “没有代码锚点也可以先把字段写死”
- “字段名先按常识脑补，后面再改”
- “关系先模糊写一下，后面再补”

这些都表示：你正在跳过核心认知，应立即回到 7 步顺序。

## Completion Check

完成一次核心认知后，至少自查：

- 是否严格按 7 个维度顺序完成，没有跳步、没有空维度
- 每一维是否达到 `Minimum Bar` 的最低完成标准
- 是否把真正影响设计决策的不确定项标成了 `待确认`
- 是否已经足以支撑后续方案、设计或实现，而不是停留在泛泛描述
- 如果当前任务本来就需要沉淀设计文档，是否已经按“功能模块 -> 实体与属性 / 关系与状态 / 功能点”组织，并且每个功能点都覆盖了 `功能`、`参与实体`、`界限`
- 如果是多子系统新系统，是否已经先完成子系统拆分，并且每个子系统都说明了它在总系统中的位置、它依赖谁、谁依赖它

## Purpose

核心认知的目的，是为后续工作建立一个稳定、一致、可扩展、可验证的理解环境：

- 稳定一致：整个工作过程中的理解不随上下文漂移
- 可扩展：新增规则、模块、行为时，有明确挂载点
- 可验证：可以独立检查认知是否完整，并据此修正错误理解
