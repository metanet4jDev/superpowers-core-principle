# Core Principle

## Overview

在头脑风暴前，先建立核心认知，再给方案。

**核心原则：** 认知必须短、准、可验证，且必须按固定顺序理解系统，避免在压力下直接跳到方案、实现或结论。

**与 `brainstorming` 的关系：** `brainstorming` 决定如何进入设计讨论；本技能决定进入讨论前必须先建立什么认知骨架。

## When to Use

**Use when：**
- 开始系统架构、功能设计、组件设计、行为修改前的头脑风暴
- 开始需求澄清、领域建模、business rules 梳理、state transition 分析时
- 需要先统一系统理解，再进入方案、拆解、设计或实现
- 面对复杂业务规则、状态流转、实体关系、边界条件时
- 用户要求“先想清楚再做”或场景本身容易误改行为时

**Do not use when：**
- 只是查一个现成 API、命令或语法
- 只是做机械替换，没有系统理解成本
- 只需要遵循 brainstorming 的对话流程，而不需要额外澄清实体、状态、界限

## Core Pattern

必须按下面顺序建立认知，不能跳步，不能重排：

| 顺序 | 维度 | 必须回答的问题 |
| --- | --- | --- |
| 1 | 结构 | 系统、子系统、模块、组件如何分层和协作？ |
| 2 | 分类 | 有哪些关键实体？它们如何命名和归类？ |
| 3 | 关系 | 实体之间依附、关联、约束关系是什么？ |
| 4 | 属性 | 关键实体有哪些属性？类型、唯一、可变、必填、长度、精度是什么？ |
| 5 | 状态 | 初始、中间、最终状态是什么？状态如何迁移和约束？ |
| 6 | 功能 | 系统提供什么能力？每个功能的目的是什么？ |
| 7 | 界限 | 功能会改变哪些属性和状态？什么条件决定功能可用或不可用？ |

如果某一步说不清，就不要进入下一步。

## Quick Reference

在头脑风暴中，先用最少文字输出这 7 项：

```text
结构：
分类：
关系：
属性：
状态：
功能：
界限：
```

界限必须至少覆盖两类判断：
- 功能会引起哪些属性和状态变化，如何变化
- 属性和状态如何反过来限制功能是否可用

## Implementation

### 输出要求

- 文字少、准确、精要、目的明确、可验证
- 优先从现有代码、目录、命名、状态流转中提取认知，不额外制造文档
- 如果代码已经能表达，就不要重复维护额外说明
- 如必须补充说明，只写准确、简洁的注释或最小文档

### 推荐表达模板

```markdown
结构：订单域、支付域、履约域；支付回调驱动订单状态更新，履约只消费可发货订单。
分类：订单、支付单、发货单三个核心实体。
关系：一个订单可关联多个支付单；发货资格依赖订单与支付状态。
属性：支付单包含 amount、paidAmount、status、channel；status 必填且可变，amount 为高精度金额。
状态：支付单从待支付 -> 部分支付 -> 已支付 -> 已退款；订单从待支付 -> 待发货 -> 已发货。
功能：支付确认、发货校验、退款回调；目的分别是收款、控发货、纠正资金状态。
界限：未支付或部分支付时不可发货；退款后订单需回退为不可发货或进入异常处理。
```

### 示例

场景：修改“部分支付后可发货”的业务行为。

```markdown
结构：支付模块负责资金状态，订单模块负责发货资格，履约模块只执行已放行订单。
分类：订单、支付单、发货指令。
关系：支付单状态影响订单状态，订单状态决定发货指令是否允许创建。
属性：支付单包含应付金额、实付金额、支付状态；订单包含发货资格标记。
状态：未支付、部分支付、已支付、退款中、已退款。
功能：支付确认后更新订单；发货前统一校验 canShip(order)。
界限：部分支付不会直接触发发货；只有已支付订单才允许发货；退款中和已退款订单必须拦截发货。
```

## Common Mistakes

| 错误 | 修正 |
| --- | --- |
| 直接给方案，不先建立认知 | 先按 7 个维度输出最小认知骨架 |
| 只讲功能，不讲实体、状态、界限 | 补齐分类、属性、状态、界限后再继续 |
| 把“界限”写成泛泛风险 | 明确“什么变化会发生”与“什么条件禁止功能” |
| 为了说明问题新建很多文档 | 先读代码，能从代码表达就不额外维护 |
| 因为时间紧就省略认知步骤 | 时间越紧，越要先固定认知顺序 |

## Red Flags

- “先直接给方案，后面再补理解”
- “用户要求简洁，所以分类、状态、界限先不写”
- “大概知道系统怎么跑就够了”
- “先写功能清单，实体和状态之后再补”
- “多写一份文档更保险”

这些都表示：你正在跳过核心认知，应立即回到 7 步顺序。

## Purpose

核心认知的目的，是为后续工作建立一个稳定一致、可扩展、可验证的结构：

- 稳定一致：整个工作过程中的理解保持一致，不随上下文漂移
- 可扩展：新增规则、模块、行为时，有明确挂载点
- 可验证：可以独立检查认知是否完整，并据此修正错误理解
