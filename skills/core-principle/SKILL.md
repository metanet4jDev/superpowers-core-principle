# Core Principle

## Purpose

建立“核心认知”：在方案、详细设计、计划和实现前，先说清系统的稳定事实、关键状态和边界条件。

硬规则：

- 先认知，后方案；先事实，后动作。
- 每个结论要有来源锚点；推测写 `待确认`。
- 同一事实只能有一个主落点，其他章节只引用。
- 本技能只回答“系统是什么样”，不替代 `brainstorming`、`writing-detailed-design` 或 `writing-plans`。

## Skill Boundary

| 技能 | 主职责 |
| --- | --- |
| `core-principle` | 7 维认知、术语、持久化事实、状态、全局不变量 |
| `brainstorming` | 澄清需求、比较方案、取得设计批准 |
| `writing-detailed-design` | 写详细设计和配套产物；引用核心认知 |
| `reviewing-design-artifacts` | 用户明确要求时，检查核心认知和详细设计产物 |
| `writing-plans` | 从已批准设计生成实现计划；用户要求时审查计划 |

核心认知变化若影响已存在的设计或计划，先同步设计；计划受影响时再同步计划。不同步不得继续实现。

## When to Use

Use when:

- 头脑风暴开始前，需要统一问题边界。
- 探索现有代码库会影响架构、模块、状态或规则判断。
- 准备做架构、功能、组件或行为变更。
- 用户要求建立、更新或审查核心认知。
- 出现新证据、新约束或认知冲突。

Skip when:

- 只是查询 API、命令或语法。
- 只是纯格式化、纯重命名或机械替换。
- 当前只是在执行已批准计划，且认知无新增事实或冲突。

## 7-Dimension Order

必须按顺序建立，不跳步、不重排、不整维留空。

| 顺序 | 维度 | 必须回答 |
| --- | --- | --- |
| 1 | 结构 | 系统、子系统、模块如何分层协作？谁是事实源？ |
| 2 | 分类 | 有哪些关键实体？如何命名和归类？ |
| 3 | 关系 | 谁依附谁、谁定位谁、谁约束谁？基数是什么？ |
| 4 | 属性 | 关键属性的类型、唯一性、可编辑性、必填、长度/精度、枚举值是什么？ |
| 5 | 状态 | 初始态、中间态、终态、迁移触发、失败/拒绝/超时/终止约束是什么？ |
| 6 | 功能 | 系统提供哪些能力？动作、目的、作用对象是什么？ |
| 7 | 界限 | 什么条件下可用或不可用？输出、关系/属性/状态变化、异常是什么？ |

最小骨架：

```text
结构：
分类：
关系：
属性：
状态：
功能：
界限：
```

`界限` 在核心认知中只表达全局可用条件和后果，不展开单个功能点的编号场景。可用这 4 类组织：

- 输入/前置：输入契约、实体关系、关键属性、初始状态。
- 触发/判断：关键条件、关系取值、属性取值、状态取值、决策结果。
- 结果：输出、关系变化、属性变化、状态变化。
- 异常：异常、拒绝、失败、超时、终止。

单功能点的 `given / when / then / exception / verify` 放在详细设计。

## Minimum Bar

| 维度 | 最低标准 | 常见缺漏 |
| --- | --- | --- |
| 结构 | 分层、职责、协作链路、事实归属 | 只列模块名 |
| 分类 | 列出关键实体 | 只写“数据、流程、配置” |
| 关系 | 写清依附、定位、约束方向和基数 | 只说“有关联” |
| 属性 | 属性挂到实体，并说明约束和判断作用 | 只堆字段名 |
| 状态 | 写清状态集合、迁移、禁止迁移和终态 | 只有状态名 |
| 功能 | 写清动作、目的、作用对象 | 只写“支持新增/编辑/删除” |
| 界限 | 写清条件、决策、变化和异常 | 只讲风险 |

## Core-Cognition Document Contract

核心认知固定写入独立文档 `CORE_COGNITION_PATH`；详细设计只引用它，不内嵌全文。核心认知用 7 个标题承载 7 维语义和术语约束：

| 标题 | 承载内容 | 不写什么 |
| --- | --- | --- |
| `结构` | 系统位置、事实归属、依赖关系、单一事实源 | 调用步骤、方法编排 |
| `术语与命名` | 业务术语、实体名、状态名、接口语义名、禁止别名 | 局部变量名、临时实现类名 |
| `持久化数据模型` | 持久化实体 + 关键属性，承载 `分类 + 属性` | 临时 DTO/Command/VO，除非它本身是稳定契约 |
| `持久化关系` | 依附、基数、唯一键、归属、约束 | 实现层调用关系 |
| `持久化状态` | 状态集合、迁移触发、禁止迁移、失败/拒绝/超时/终止态 | 业务时序全文 |
| `功能` | 功能名、一句话目的、章节引用 | 参与实体、执行路径、`given/when/then/verify` |
| `全局约束` | 跨功能、跨模块、不能归属到单个功能点的不变量 | 单个功能点的局部规则 |

`术语与命名` 是全局命名事实源。详细设计、API、DDL、时序图、测试和代码注释必须使用同一术语；确需别名时，只能在此处声明映射和适用边界。

状态存在多分支、回退、拒绝、超时、重试或并行汇合时，核心认知只写稳定状态集合和迁移约束；图示、时序和功能点细节交给详细设计。

## Single-Source Rules

| 信息类型 | 主落点 |
| --- | --- |
| 稳定事实、持久化事实、跨功能不变量 | 核心认知 |
| 实现编排、时序、调用顺序 | 详细设计 |
| 单个功能规则 | 功能点详细设计 |
| 单元级验证 | 功能点 `verify` |
| 集成/端到端验收 | 验收章节 |
| 可执行实现步骤 | 实现计划 |

其他位置只能引用，不能复制展开。发现重复时，保留主落点，删掉或改写其他章节。

## Continuous Loop

- `V0`：探索或头脑风暴前，先写 7 维最小骨架。
- `V1..Vn`：新需求、新代码证据或冲突出现时，增量更新相关维度并标来源。
- `Vfinal`：进入详细设计或计划前，收敛会影响设计、测试、实现的 `待确认`。

信息不足时写 `待确认`，并说明缺哪个实体、关系、属性、状态、条件或数字。真实字段名未确认时，先写业务含义，再标 `字段名待确认`。默认值、阈值、TTL、重试次数、超时预算、SLA 等精确数字必须标来源：`代码` / `配置` / `历史观测` / `需求` / `待确认`。
术语不统一时，先在 `术语与命名` 中确定主术语，再继续设计；不能在详细设计中临时发明平行名词。

## Completion Check

- 7 维是否按顺序完成，且无空维。
- 每一维是否达到最低标准。
- 关键实体、关系、属性、状态是否有来源或 `待确认`。
- 术语与命名是否覆盖核心实体、状态、接口语义和禁止别名。
- `功能` 是否只写能力，`界限` 是否写清条件和后果。
- 核心认知、详细设计、计划是否遵守单一事实源。

用户明确要求验证核心认知时，使用 `validation-checklist.md`；只检查核心认知本身，不检查功能点详细设计。
