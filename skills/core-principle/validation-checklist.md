# Core Principle Validation Checklist

仅在用户明确要求验证核心认知时使用。不要自动触发。

本清单只检查核心认知本身，不检查功能点详细设计、接口字段、DDL、时序图、计划或代码实现。

## 验证步骤

### 1. 文档边界

- 核心认知是否位于独立 `CORE_COGNITION_PATH`。
- 是否只沉淀稳定事实、持久化事实、状态和跨功能不变量。
- 是否没有展开实现编排、接口全字段、单个功能点规则、`verify` 或实现步骤。
- 详细设计需要使用的核心事实是否能在本文件定位。

### 2. 7 维是否完整

逐项检查，不能整维缺失：

- `结构`：系统/子系统/模块位置、事实归属、依赖、单一事实源。
- `分类`：关键实体清单，不用“数据/流程/配置”替代实体。
- `关系`：依附、基数、唯一定位、约束方向。
- `属性`：属性归属到实体，写清类型、唯一性、可编辑性、必填、长度/精度、判断作用。
- `状态`：状态集合、初始/中间/终态、迁移触发、禁止迁移、失败/拒绝/超时/终止。
- `功能`：能力总览、目的、作用对象或详细设计章节引用。
- `界限`：全局可用条件、禁用条件、状态/关系/属性变化约束、异常边界。

### 3. 7 标题是否符合承载规则

核心认知应使用或等价覆盖：

1. `结构`
2. `术语与命名`
3. `持久化数据模型`
4. `持久化关系`
5. `持久化状态`
6. `功能`
7. `全局约束`

必须满足：

- `术语与命名` 承载业务术语、实体名、状态名、接口语义名和禁止别名。
- `持久化数据模型` 承载 `分类 + 属性`。
- 真实字段名未确认时，先写业务含义，再标 `字段名待确认`。
- `功能` 只写能力总览，不写参与实体、执行路径、`given / when / then / verify`。
- `全局约束` 只写跨功能、跨模块的不变量。

### 4. 持久化事实是否优先

检查核心实体是否优先来自持久化数据、持久化配置、稳定外部契约或明确需求事实。

DTO、Command、VO、Service 临时对象进入核心认知时，必须说明它本身是稳定契约；否则应下沉到详细设计。

### 5. 单一事实源是否成立

对每条关键事实定位主落点：

| 信息类型 | 合法主落点 |
| --- | --- |
| 稳定事实、持久化事实、跨功能不变量 | 核心认知 |
| 实现编排、时序、调用顺序 | 详细设计 |
| 单个功能规则 | 功能点详细设计 |
| 单元验证 | 功能点 `verify` |
| 集成/端到端验收 | 验收章节 |
| 执行步骤 | 实现计划 |

发现同一实体、属性、关系、状态或全局约束在多个位置重复展开时，标记为问题。
