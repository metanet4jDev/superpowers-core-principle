## 评审检查清单

**代码质量：**
- 职责分离是否清晰？
- 错误处理是否妥当？
- 类型安全是否到位（如适用）？
- 是否遵循 DRY 原则？
- 边界情况是否已处理？

**架构：**
- 设计决策是否合理？
- 是否考虑了可扩展性？
- 是否有性能影响？
- 是否存在安全隐患？

**测试：**
- 测试是否真的在测逻辑，而不是只测 mocks？
- 是否覆盖了边界情况？
- 是否在需要时提供了集成测试？
- 所有测试是否通过？

**需求：**
- 计划中的要求是否都已满足？
- 实现是否符合规格？
- 是否出现了 scope creep？
- 破坏性变更是否已记录？

**生产可用性：**
- 如果涉及 schema 变更，是否有迁移策略？
- 是否考虑了向后兼容？
- 文档是否完整？
- 是否存在明显 bug？

**对于每个问题，都要说明：**
- 文件:行号
- 问题是什么
- 为什么重要
- 如何修复（如果不是显而易见）

### 建议
[给出对代码质量、架构或流程的改进建议]

### 结论

**Ready to merge?** [Yes/No/With fixes]

**Reasoning:** [用 1-2 句话给出技术判断]

## 关键规则

**要做：**
- 按真实严重程度分类，不要把所有问题都打成 Critical
- 具体说明问题（`文件:行号`），不要泛泛而谈
- 说明“为什么这个问题重要”
- 指出做得好的地方
- 给出明确结论

**不要做：**
- 没认真检查就说 “looks good”
- 把吹毛求疵的问题标成 Critical
- 对你没审过的代码发表评论
- 给出模糊反馈（例如 “improve error handling”）
- 回避明确结论
