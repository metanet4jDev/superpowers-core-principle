# 编写轻量实现计划

## 边界与模式

为无需详细设计的任务生成可执行计划。仅在用户明确要求时使用；模式由用户决定，技能不得判断复杂度。

| 用户指定 | 模式 | 事实源 |
| --- | --- | --- |
| `L0`、无需核心认知 | L0 | 任务事实摘要 |
| `L1`、需要核心认知 | L1 | 独立核心认知文档 |
| `L2`、复杂任务 | 不支持 | 完整设计和 `writing-plans` 流程 |

用户未指定或表达含糊时，只问：

> "本次轻量计划使用 L0 还是 L1？"

即使用户要求“自己决定”、时间紧急或模式看起来明显，也不得代选、默认、改判或升级。用户选定后声明：

> "我正在使用 writing-lightweight-plans 技能编写轻量实现计划。"

硬规则：

- L0 不创建核心认知；L1 必须先创建或更新核心认知。
- L0、L1 均不要求、创建或引用 Foundation Gate、详细设计及其配套产物。
- 只消费已确认事实；不得发明需求、行为、接口、状态或存储规则。
- 计划阶段不得实现。

## 路径与事实源

**REQUIRED SUB-SKILL:** Use `document-workspace-layout`.

两种模式都使用 `PLAN_PATH`、`PLAN_CHANGELOG`、`PLAN_WORKSPACE_DIR`、`TASK_WORKSPACE_DIR`。L1 还必须使用 `CORE_COGNITION_PATH`；L0 不得要求、读取或创建该文件。

遵守该技能的 `PLAN_NAME` 解析、目录创建、cwd 和 `planning-with-files-zh` 三件套规则。完整计划只写入 `PLAN_PATH`，不得拆分或另造路径。

| 模式 | 前置事实 |
| --- | --- |
| L0 | 计划头部记录目标、范围、现状证据及来源锚点、约束、不做事项、验收标准。缺少影响行为的事实时停止询问，不得推测。 |
| L1 | **REQUIRED SUB-SKILL:** Use `core-principle` before planning. 核心认知必须达标；关键事实有来源或 `待确认`；阻塞项先收敛。计划只按章节引用，不复制稳定事实。 |

## 计划准备

定义任务前：

1. 切换到 `TASK_WORKSPACE_DIR`，核对真实文件、测试、现有模式和仓库状态。
2. 列出新建、修改、测试文件及职责。
3. 按依赖顺序拆分独立、可验证的任务。
4. 区分编码和非编码任务，使用对应模板。

计划必须给出准确路径、具体动作和验证语义；不得写实际实现代码、测试代码、具体测试命令、验证命令或提交命令。

已执行、执行中或已被下游消费的计划只能新增增量计划并更新 `PLAN_CHANGELOG`，不得覆盖原计划。

## 计划头部

`PLAN_PATH` 必须以以下信息开头：

```markdown
# [功能名称] 轻量实现计划
> **计划模式：** L0 / L1
> **事实源声明：** [L0：任务事实摘要；L1：核心认知文档绝对路径及章节]
> **详细设计声明：** 本计划不依赖详细设计，不得扩展已确认事实。
>
> **给执行代理的要求：** 使用 `subagent-driven-development`（支持子代理时）或 `executing-plans` 执行。所有步骤使用复选框（`- [ ]`）跟踪。

- **目标：** [可观察结果]
- **范围：** [允许修改的范围]
- **不做事项：** [明确排除项]
- **验收标准：** [可验证完成条件]

**代码仓库与分支：**
- 代码仓库：[仓库本体绝对路径]
- 开发目录：[日常代码读写绝对路径]
- 开发分支：[分支名]
```

L0 紧接头部写“任务事实摘要”；L1 写 `CORE_COGNITION_PATH` 绝对路径和引用章节。不得伪造详细设计路径。

## 任务顺序闸门

计划必须包含：

```markdown
### 0. 任务顺序闸门（强制）

- [ ] 当前任务所有步骤完成后，将当前任务所有复选框标记为 `[x]`。
- [ ] 当前任务未标记完成前，不得开始下一个任务。
- [ ] 编码任务必须先完成 TDD、规范审查、问题修复和提交，才能标记完成。
```

## 编码任务模板

每个编码任务必须保留完整 TDD、代码和测试审查、问题修复、逐任务提交。任务小、线上紧急、经理要求或时间不足都不能删除这些步骤。

````markdown
### 任务 N：[组件名称]
**事实来源：** [L0 事实摘要条目；或 L1 核心认知章节]
**涉及文件：**
- 新建：`exact/path/to/file`
- 修改：`exact/path/to/existing:line`
- 测试：`exact/path/to/test`

- [ ] **步骤 1：列出单元测试**

**单元测试清单：**
- `test-file::test_name`：覆盖 [行为、边界或异常语义]

**预期验证语义：**
- 失败验证：测试先以符合预期的原因失败。
- 通过验证：最小实现和必要重构后，相关测试通过，行为与事实来源一致。

- [ ] **步骤 2：按 TDD 完成测试与实现**
使用 `test-driven-development` 完成 RED、GREEN、REFACTOR；不得跳过失败验证。

- [ ] **步骤 3：按仓库规范审查代码和测试，并修复问题**
读取并应用当前仓库的代码、测试规范。修复全部问题后再提交。

- [ ] **步骤 4：提交当前任务**
只提交当前任务相关改动，不写具体提交命令。

- [ ] **最终步骤：标记任务 N 已完成，再进入任务 N+1**
````

## 非编码任务模板

非编码任务不强制 TDD、代码审查或逐任务提交，但仍受任务顺序闸门约束。

```markdown
### 任务 N：[产物名称]
**事实来源：** [L0 事实摘要条目；或 L1 核心认知章节]
**涉及文件：**
- 新建：`exact/path/to/file`
- 修改：`exact/path/to/existing`

- [ ] **步骤 1：[具体动作]**
- [ ] **步骤 2：按预期语义验证产物**
- [ ] **最终步骤：标记任务 N 已完成，再进入任务 N+1**

**预期验证语义：**
- [内容、格式、引用或行为的具体完成条件]
```

## 禁止项

- 禁止 `TBD`、`TODO`、`implement later`、`fill in details`、“类似任务 N”。
- 禁止无具体字段、条件和错误语义的“添加校验/处理异常”。
- 禁止无测试文件、方法和场景的“补充测试”。
- 禁止只写“做什么”不写“怎么做”、复制 L1 核心认知、把 L0 摘要伪装成完整核心认知。

## 审查与纠偏

> "轻量计划已完成并保存到 `<PLAN_PATH>`。如果需要我审查计划，请直接告诉我。"

保存计划后只输出上句。仅当用户明确要求 review、审查或检查计划时执行；检查模式与事实源、路径、可执行性、编码质量闸门、占位符和事实扩展。修改后是否复审仍由用户明确触发。

| 红旗或借口 | 纠正 |
| --- | --- |
| 用户让我决定；模式看起来明显 | 只问 L0/L1，不得推断或改判。 |
| L1 核心认知以后补 | 核心认知是前置事实源，必须先完成。 |
| 任务复杂，应自动升级 | 用户决定模式；技能不得升级。 |
| 改动少或紧急，可省测试/审查 | 编码任务始终保留 TDD、审查、修复、提交。 |
| 没有详细设计，计划里补全 | 计划不能充当隐藏设计；缺事实就停止询问。 |
| 正在创建 Foundation Gate/详细设计，或用推测补事实 | 立即停止并回到指定模式和事实源。 |

## 完成检查

- 模式未改判；路径和事实源符合对应契约；`PLAN_PATH` 是唯一入口。
- 计划不依赖详细设计、不扩展事实、无占位符；每个任务可执行、可验证。
- 编码任务保留 TDD、审查、修复、逐任务提交；非编码任务未误套这些闸门。
